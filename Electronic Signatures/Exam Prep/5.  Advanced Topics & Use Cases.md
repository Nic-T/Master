# Advanced Topics & Use Cases

## 1. Remote Qualified Electronic Signatures (Remote QES)

The industry has shifted from "Local Signing" (physical USB token or smart card) to "Remote Signing" (private keys stored on a server). Understand trade-offs and architecture.

### Local vs Remote

- **Local:** User holds the private key physically (e.g., USB token). Requires drivers and hardware ports; less mobile-friendly.
- **Remote (Cloud):** Key stored in an HSM at a Trust Service Provider (TSP). Mobile-friendly, no local drivers, potentially lower cost.

### The "Sole Control" Challenge

- For a signature to be _Qualified_, the signatory must have sole control over their private key.
- Remote signing uses a Signature Activation Module (SAM) and strong user authentication (2FA/OTP) to ensure the user authorizes each signing transaction while the key remains in the TSP/HSM.

## 2. Remote Signing Architecture & Standards

### SCAL (Sole Control Assurance Level)

- **SCAL 2:** Highest level; requires SAM to operate in a tamper-protected environment alongside the HSM.

### CSC (Cloud Signature Consortium) Protocol

- Standard API for connecting signature clients to a TSP.
- Key endpoints to recognize:
  - `/credentials/list` — list available certificates
  - `/credentials/authorize` — obtain a token to access a key
  - `/credentials/signHash` — perform the signing operation
- Authorization typically uses OAuth 2.0.

## 3. Preservation Services (Long-Term Validation)

Digital signatures are only mathematically valid while certificates and algorithms remain trustworthy. Preservation services extend trust over long periods.

- Problem: Certificates expire; CAs may stop publishing old CRLs; algorithms weaken over time.
- Solution (eIDAS Article 34): Timestamp signatures and validation data (RFC 3161) while certificates are valid; periodically re-timestamp or re-sign archives using stronger algorithms.

## Advanced Signature Profiles (ES Hierarchy)

- **BES (Basic Electronic Signature):** Contains the signer's signature and certificate; relies on external revocation/validation lookups.
- **ES-T (Timestamped):** BES + trusted timestamp proving existence at a time.
- **ES-C (Complete):** ES-T + references or embedded copies of validation data (certificates, CRLs, OCSP).
- **ES-X (Extended):** ES-C + timestamps over the validation references.
- **ES-A (Archival):** Full embedded validation data and archival timestamps for long-term preservation.

## Cryptography Fundamentals — Specific Mathematical Nuances

- **Blind Signatures (David Chaum):** Privacy-preserving signing (e-voting, digital cash). RSA-style blind signing uses a blinding factor $k$ so the signer signs blinded $m^*$; the requester unblinds to obtain a valid signature for $m$. Risk: blind signing can be abused; avoid key reuse across signing/encryption.
- **ECC Field Types:**
  - Prime curves ($\mathbb{F}_p$): integers modulo a prime $p$ — common for software.
  - Binary curves ($\mathbb{F}_{2^m}$): polynomial basis over GF(2) — common in hardware.
  - Point at infinity ($O$): identity element of the group; $P + (-P) = O$.

## PKI Topologies & Trust Anchors

- **Cross-Certification (Mesh):** Reciprocal trust links between CAs; scales poorly for many domains.
- **Bridge CA (Hub):** Central authority that connects multiple PKI domains (e.g., Federal Bridge CA), simplifying relationships.
- **Trust Lists:**
  - **EUTL:** European Trust List — legal backbone for EU Qualified Signatures.
  - **AATL:** Adobe Approved Trust List — commercial trust list used by Adobe; not identical to EUTL.

## Cryptographic Algorithm Trivia (Quick Facts)

- **DES:** Based on a Feistel network; uses a 56-bit key historically.
- **AES (Rijndael):** Supports 128/192/256-bit keys.
- **Brute-force anecdote:** AES-256 brute force is described as requiring astronomically infeasible energy (slide text: "energy of 150 huge nuclear reactors running longer than the age of the universe"). This illustrates practical infeasibility, not an exact physical bound.

## Summary Checklist

- Know the ES hierarchy (BES → ES-T → ES-C → ES-X → ES-A) and what each level adds.
- Understand preservation: timestamping (RFC 3161), embedding validation data, and periodic re-timestamping/re-signing for long-term validity.
- Remember blind signature basics and associated risks (do not reuse signing/encryption keys).
- Distinguish ECC field types (prime vs binary) and understand the point at infinity.
- Recognize PKI topologies: cross-certification (mesh) vs bridge CA (hub), and differences between EUTL and AATL.

## 4. Industry Case Studies

The lecture materials provide specific examples of how PKI is applied in different sectors.
• Fintech (Banking):
◦ Banks use existing "Know Your Customer" (KYC) data to enroll users for certificates, simplifying the Registration Authority (RA) process.
• Automotive (V2X - Vehicle to Everything):
◦ Cars communicate with traffic infrastructure (traffic lights, etc.).
◦ Privacy: To prevent tracking a specific car, the system uses Pseudonym CAs that issue short-lived certificates, separating the vehicle's real identity from its operational messages.
• Drones (UAVs):
◦ Project SENTINEL: Uses PKI for flight approval. A drone and a ground station perform a key agreement to authorize the flight path.
◦ Drone Certificates: These are simplified certificates containing the Issuer and Subject (Drone ID), valid for specific periods.
• WYSIWYS (What You See Is What You Sign):
◦ A security concept ensuring that the document displayed on the screen is exactly what the user is cryptographically signing, preventing malware from showing one contract but signing another.
